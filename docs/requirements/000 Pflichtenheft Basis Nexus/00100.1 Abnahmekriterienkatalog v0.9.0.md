Diese Liste muss Punkt für Punkt für den Release Candidate bzw. die finale Version 1.0.0 validiert sein.

1. Formale Hauptkriterien (Kapitel 10.1)

Diese Kriterien bilden die "Definition of Done" für das Gesamtprojekt.

    1.1 Vollständigkeit: Alle in Kapitel 4 spezifizierten Features sind implementiert.

    Qualität: Alle nicht-funktionalen Anforderungen (Performance, Security, etc.) aus Kapitel 5 sind erfüllt.

    Tests: Die automatisierte Test-Suite läuft fehlerfrei durch; Code-Coverage-Ziele sind erreicht.

    Fehlerfreiheit: Es existieren keine bekannten offenen Bugs im Mantis-Bugtracker (Zero-Bug-Policy für v1.0.0).

    Dokumentation: Die technische Dokumentation (Kapitel 12) liegt in finaler Version vor.

2. Detaillierte Funktionale Kriterien (Kapitel 4)

Das Basisframework muss folgende technische Funktionen bereitstellen:
2.1 Basisframework Core

    Routing & Rendering: Anfragen werden über Controller an Twig-Templates geleitet und als HTML ausgeliefert.

    Internationalisierung (i18n): Ein TranslatorService ist implementiert, der Sprachdateien (/translations/de.php etc.) lädt und erweiterbar für DB-Provider ist.

    Compliance: Ein zentraler ConsentService verwaltet Nutzerzustimmungen; ein rudimentäres Cookie-Banner ist vorhanden.

2.2 Sicheres Session-Management (Kritisch!)

Der SessionService muss zwingend folgende Sicherheitsmerkmale aufweisen:

    Isolation: Nutzung von "Bags" (Security Bag, Attribute Bag, Flash Bag).

    Unabhängigkeit: Kein direkter Wrapper um $_SESSION, Nutzung von SessionHandlerInterface.

    ID-Sicherheit: Mind. 128 Bit Entropie, generiert via random_bytes().

    Lifecycle: Implementierung von regenerateId() (bei Login/Privilegienwechsel) und invalidate().

    Fingerprinting: Hash aus Browser, OS, IP (anonymisiert) wird geprüft; bei Abweichung Invalidation.

    Timeout: Strict Idle Timeout (z.B. 30 Min) & Absolute Max Lifetime.

    Cookie-Flags: HttpOnly, Secure, SameSite=Strict, kein PHPSESSID als Name.

    CSRF: Automatische Token-Generierung und -Prüfung, gekoppelt an die Session.

2.3 SEO-Grundlagen

    Meta-Daten: Individuelle <title> und Meta-Description pro Seite möglich.

    Sitemap: Automatische Generierung einer sitemap.xml.

    Robots: Standardmäßige robots.txt vorhanden.

    Canonical: Automatisches Setzen von rel="canonical".

3. Nicht-Funktionale Kriterien (Kapitel 5)
3.1 Performance KPIs

    Server: TTFB (Time To First Byte) ≤ 500ms (ungecacht).

    Client: LCP (Largest Contentful Paint) < 2,5 Sekunden.

    DB-Last: Max. 20 SQL-Abfragen pro typischer Detailseite.

    Assets: CSS/JS müssen minifiziert und gebündelt ausgeliefert werden.

3.2 Sicherheit (Defense in Depth)

    HTTPS: Zwingende Erzwingung im Produktionsmodus (Abbruch bei HTTP).

    Passwörter: Speicherung ausschließlich mit Argon2id.

    Secrets: Keine Secrets im Git; Verwaltung nur über Environment-Variablen (.env).

    Schutz: XSS (Twig Escaping), SQLi (Prepared Statements) und CSRF-Schutz aktiv.

3.3 Architektur & Code-Qualität

    Stateless: Keine benutzerspezifischen Daten (Sessions) im lokalen Dateisystem des Webservers (Vorbereitung für Redis/DB-Storage).

    Standards: Einhaltung PSR-12, Strict Types, Hexagonale Architektur.

    Static Analysis: PHPStan (oder vergleichbar) läuft im Build-Prozess ohne Fehler.

3.4 Usability (Endnutzer)

    Responsive: Optimale Darstellung auf Desktop, Tablet, Mobile.

    A11y: WCAG 2.1 (Level AA) Konformität (Semantik, Kontraste, ARIA wo nötig).

    Feedback: Visuelle Ladeindikatoren bei Wartezeiten, Toast-Messages bei Erfolg/Fehler.

4. Qualitätssicherung & Tests (Kapitel 9)

    Test-Suite: Alle Unit- und Integrationstests laufen im CI-Prozess erfolgreich durch.

    Code Coverage: > 90% Abdeckung für die kritische Domain-Logik.

    CI/CD: Der Build-Prozess (inkl. Asset-Kompilierung) läuft vollautomatisiert über npm run build / Composer.

5. Dokumentation (Kapitel 12)

Die folgenden Dokumente müssen im Repo (/docs) vorhanden und aktuell sein:

    Entwickler-Handbuch: Setup, Architektur, Config, Verwendung der Kern-Services.

    API-Referenz: DocBlocks im Code vollständig vorhanden.

    ADRs: Wichtige Architekturentscheidungen sind in /docs/adr festgehalten.

6. Webserver-Checkliste (für Go-Live)

Vor dem Switch auf Produktion zu prüfen:

    SSL: Zertifikat validiert.

    Favicon: favicon.ico liegt physisch in /public (vermeidet 404-Logs).

    Statische Assets: Webserver liefert Assets direkt aus (Bypass von PHP via .htaccess o.ä.).
